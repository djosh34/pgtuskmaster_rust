## Task: Rewrite Logging Around A Custom `LoggableEvent` Derive, Logger-Owned Global Context, Flat OTel-Friendly Attributes, And An Exhaustive Event Set <status>completed</status> <passes>true</passes>

<description>
**Goal:** Replace the current logging trait-and-visitor design with a much simpler and stricter model:
- events become loggable through a custom derive and `#[]` tags
- emitters do not handwrite `into_log_event()` implementations
- emitters do not use `serde` as the event-to-log conversion mechanism
- logger-global context such as hostname, cluster name, scope, and member id is injected by the logger, not emitted by domains
- final log records use flat attributes rather than nested `context` / `fields` blobs, so the output stays aligned with OpenTelemetry-style querying and remains easy to consume from Grafana/Loki

The higher-order goal is to make logging compiler-driven and ultra-simple:
- log event meaning is declared once on the enum variant with attributes
- field extraction is generated by a proc-macro
- the final record shape is flat, predictable, and query-friendly
- the generic logging interface is not shaped by one domain's needs such as `job_id`, `binary`, or function-name origins

This task intentionally replaces the current logging architecture. The existing system already moved to typed domain log events, but it is still too manual and too logging-centric:
- `DomainLogEvent` still has two methods, `metadata()` and `write_fields()`
- event implementations still duplicate logic across two large match trees
- `LogFieldVisitor` still leaks logging internals into emitters
- node-global fields such as `scope` and `member_id` still appear in event payloads
- some log fields are weakly named, especially `error`
- there are still log-only wrapper types such as `ProcessExecutionIdentity`, `ProcessJobIdentity`, `RuntimeNodeIdentity`, and `DcsLogIdentity`
- there are still function-name origin enums that exist only for logging
- the last task version proposed nested `fields` objects and serde-tag splitting; that is no longer the required direction

The required end state from this task is:
- one real logging trait: `LoggableEvent`
- one custom derive macro: `#[derive(LoggableEvent)]`
- one custom field-value derive macro: `#[derive(LogValue)]`
- event names, severity, result, message, source, and field rename/flatten rules are declared via attributes
- event fields are turned into flat log attributes by generated code, not by serde-tag introspection
- final emitted records are flat JSON objects with flat attribute keys
- there is no nested `context` object
- there is no nested `fields` object
- `bytes_len` is removed from subprocess/process log events because the line text is already emitted
- no log event enum exists outside the exhaustive set defined in this task

Anything in the repo that is still a log event after this task, and is not listed explicitly below, must be removed or folded into one of the listed event enums. This task is the authoritative and exhaustive log-event inventory.

**Design decisions already made from user discussion:**
- Built-in Rust attributes do nothing by themselves; a custom derive or attribute macro must interpret them.
- Using a custom proc-macro here is acceptable and desirable. This is the same general category of technique as `thiserror`: a proc-macro removes repetitive boilerplate while preserving explicit types.
- The event-to-log conversion path must not require serde.
- The proc-macro attribute vocabulary must be strongly validated at compile time. Spelling variants such as `warning`, `WARN`, `Warning`, or any other unsupported token must fail compilation. Only the exact allowed strings listed in this task are accepted.
- The final record shape should avoid nested structures because flat attributes are easier to query and fit OpenTelemetry/Grafana expectations better.
- Flat does not mean anonymous. Non-core output fields should use dotted namespacing such as `event.name`, `source.producer`, and `host.name` instead of bare generic keys.
- Logger-global identity belongs to the logger, not to emitters.
- `job_id` is process-domain-specific and must not shape the generic logging interface.
- `binary` is not valuable enough to keep as a first-class log field in the final design.
- `bytes_len` should be removed; once the actual line text is logged, its byte count is redundant noise.
- Bootstrap/configuration failures remain typed bootstrap errors, not runtime log events. Logging cannot emit log events before logging has bootstrapped successfully.

**Exact required target API:**

The old trait surface in `src/logging/event.rs` must be deleted and replaced with this shape:

```rust
mod sealed {
    pub trait Sealed {}
}

pub(crate) trait LoggableEvent: sealed::Sealed + Send + 'static {
    fn into_log_event(self) -> LogEventDto;
}

pub(crate) trait LogValue {
    fn into_log_field_value(self) -> LogFieldValue;
}

#[derive(Clone, Debug, PartialEq)]
pub(crate) struct LogEventDto {
    pub(crate) severity: LogSeverity,
    pub(crate) event_name: &'static str,
    pub(crate) result: LogEventResult,
    pub(crate) message: std::borrow::Cow<'static, str>,
    pub(crate) source: LogSource,
    pub(crate) fields: Vec<LogField>,
}

#[derive(Clone, Debug, PartialEq)]
pub(crate) struct LogField {
    pub(crate) key: &'static str,
    pub(crate) value: LogFieldValue,
}

#[derive(Clone, Debug, PartialEq, serde::Serialize)]
#[serde(untagged)]
pub(crate) enum LogFieldValue {
    String(String),
    Bool(bool),
    I64(i64),
    U64(u64),
    Json(serde_json::Value),
}
```

This is a deliberate design decision:
- there is one trait method only: `into_log_event(self)`
- event authors do not handwrite that method in ordinary cases
- generated code from `#[derive(LoggableEvent)]` implements it
- there is no `metadata()` method
- there is no `write_fields()` method
- there is no `LogFieldVisitor`
- there is no requirement that event conversion go through serde

`LogEventDto`, `LogField`, and `LogFieldValue` must not be re-exported from `src/logging/mod.rs`. They are crate-internal implementation details for the derive-generated impls and for `LogSender`. They should live in a dedicated private-ish core module such as `src/logging/core/event_model.rs` or `src/logging/model.rs`, and only the derive macro plus the logging backend should reference them by fully-qualified path.

Rust cannot make the return type of a crate-wide trait method completely private if implementations live in other modules, because the generated impl must still name that type. The correct target is therefore:
- `LogEventDto`, `LogField`, and `LogFieldValue` stay `pub(crate)` so derive-generated impls can refer to them
- they are not publicly re-exported from `src/logging/mod.rs`
- normal emitters never construct them directly
- only the derive macro and `LogSender` should mention them
- all handwritten construction of these types outside logging core/derive code is forbidden

**Required proc-macro design:**

This task must add an internal proc-macro crate to the repo if one does not already exist. The exact crate name may be `crates/pgtm_log_derive` or another clearly internal name, but it must stay in-repo and private to this project.

The core logging model and sender implementation must move out of the same area that contains the postgres collectors/ingesters. The repo structure must be split clearly enough that the logging definition is not mixed with postgres line collection concerns. One acceptable target is:

```text
src/logging/mod.rs
src/logging/core/mod.rs
src/logging/core/event_model.rs
src/logging/core/sender.rs
src/logging/core/sink.rs
src/logging/postgres_ingest.rs
src/logging/tailer.rs
src/logging/postgres_ingest/
```

The exact filenames may differ, but the architectural rule is fixed:
- core logging definitions live under a dedicated core/model area
- postgres collectors/ingesters/tailers do not own the main logging trait/type definitions
- `src/logging/mod.rs` should be a narrow composition/root module, not the place where every logging detail lives

The derive surface must look like this:

```rust
#[derive(Clone, Debug, PartialEq, Eq, LoggableEvent)]
#[log_event(producer = "app", transport = "internal", parser = "app")]
pub(crate) enum ProcessLogEvent {
    #[log_event(
        name = "process.request_received",
        severity = "debug",
        result = "ok",
        message = "process job request received"
    )]
    RequestReceived {
        job_kind: crate::process::jobs::ProcessJobKind,
    },

    #[log_event(
        name = "process.output_emit_failed",
        severity = "warn",
        result = "failed",
        message = "process subprocess output emit failed"
    )]
    OutputEmitFailed {
        job_kind: crate::process::jobs::ProcessJobKind,
        stream: CapturedStream,
        cause: String,
    },
}
```

The derive must generate:
- the `sealed::Sealed` impl
- the `LoggableEvent` impl
- flat `LogField { key, value }` extraction for all variant fields
- support for field renaming and flattening rules

The proc-macro attribute grammar must be compile-time validated. The exact accepted tokens are:

- `severity = "trace" | "debug" | "info" | "warn" | "error" | "fatal"`
- `result = "ok" | "failed" | "recovered" | "timeout"`
- `producer = "app" | "postgres" | "pg_tool"`
- `transport = "internal" | "file_tail" | "child_stdout" | "child_stderr"`
- `parser = "app" | "postgres_json" | "postgres_plain" | "raw"`
- `meta = "computed"`

Anything else must be a compile error emitted by the proc-macro with a clear message naming the unsupported token and the accepted values.

When a variant uses `meta = "computed"`, the proc-macro must ignore static metadata defaults for that variant and rely exclusively on `computed_meta(&self)`. Static enum-level defaults may still exist for sibling static variants, but they must not leak into computed variants.

The field-level attributes must look like this:

```rust
#[log(key = "raw_line")]
raw_line: String

#[log(skip)]
some_non_logged_value: Something

#[log(flatten, prefix = "postgres")]
payload: std::collections::BTreeMap<String, serde_json::Value>
```

The required field behavior is:
- fields without an explicit `#[log(...)]` attribute use the Rust field name as the log key
- `#[log(key = "...")]` renames the output key
- `#[log(skip)]` omits the field
- `#[log(flatten, prefix = "...")]` flattens map-like or object-like content into flat attributes like `postgres.session_id`, `postgres.backend_type`, etc.
- `Option<T>` fields are omitted when `None`

The field-level attribute grammar must also be validated strictly. Unsupported combinations such as `#[log(skip, flatten)]` or `#[log(flatten)]` without a supported flattenable type must fail compilation.

The derive used for field values must look like this:

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, LogValue)]
#[log_value(rename_all = "snake_case")]
pub(crate) enum ProcessJobKind {
    Bootstrap,
    BaseBackup,
    PgRewind,
    Promote,
    Demote,
    StartPostgres,
    StartPrimary,
    StartDetachedStandby,
    StartReplica,
}
```

`#[derive(LogValue)]` must generate `LogValue` impls that convert enum variants into stable strings. This is not “bad” or “too magical”; it is exactly the kind of repetitive, schema-oriented code that proc-macro derives are good at. `thiserror` is the right analogy.

`LogValue` must also be implemented directly for the primitive field types used by this logging system:
- `String`
- `&'static str`
- `bool`
- `u64`
- `u32`
- `usize`
- `i64`
- `serde_json::Value`
- `std::collections::BTreeMap<String, serde_json::Value>` for flattenable payloads if needed

`usize` must normalize into `LogFieldValue::U64`.

`meta = "computed"` is the only escape hatch from static metadata, and it must stay rare. It does not mean “free-form” and it does not mean “derive something magically”. It means the proc-macro generates a by-value `match self` arm for that variant instead of emitting fully static metadata.

The crucial ownership rule is:
- `into_log_event(self)` already consumes the event
- computed variants must preserve that by-value ownership flow
- the design must not require borrowing `&self` and then cloning owned strings only because metadata and fields are extracted in separate phases

So the task no longer requires a mandatory `fn computed_meta(&self) -> ...` hook.

Instead, the required generated-code contract is:

```rust
impl LoggableEvent for PgInfoLogEvent {
    fn into_log_event(self) -> LogEventDto {
        match self {
            Self::SqlTransition { previous, next } => {
                // generated or helper-backed by-value construction
            }
            // other static variants...
        }
    }
}
```

For computed variants, the proc-macro may:
- generate the metadata computation inline in that `match` arm, or
- call a helper that takes only the moved fields it actually needs

For example, this style is allowed and preferred over `&self`-based helpers:

```rust
impl SubprocessLogEvent {
    fn line_meta(stream: CapturedStream, line: &str) -> LogComputedMeta {
        LogComputedMeta {
            severity: match stream {
                CapturedStream::Stdout => LogSeverity::Info,
                CapturedStream::Stderr => LogSeverity::Warn,
            },
            result: LogEventResult::Ok,
            message: std::borrow::Cow::Owned(line.to_string()),
            source: LogSource {
                producer: LogProducer::PgTool,
                transport: match stream {
                    CapturedStream::Stdout => LogTransport::ChildStdout,
                    CapturedStream::Stderr => LogTransport::ChildStderr,
                },
                parser: LogParser::Raw,
            },
        }
    }
}
```

And the generated arm may look like:

```rust
Self::Line { job_kind, stream, line } => {
    let meta = Self::line_meta(stream, line.as_str());
    LogEventDto {
        severity: meta.severity,
        event_name: "process.subprocess_line",
        result: meta.result,
        message: meta.message,
        source: meta.source,
        fields: vec![
            LogField::new("job_kind", job_kind.into_log_field_value()),
            LogField::new("stream", stream.into_log_field_value()),
        ],
    }
}
```

The helper type used by computed variants must therefore be:

```rust
#[derive(Clone, Debug, PartialEq, Eq)]
pub(crate) struct LogComputedMeta {
    pub(crate) severity: LogSeverity,
    pub(crate) result: LogEventResult,
    pub(crate) message: std::borrow::Cow<'static, str>,
    pub(crate) source: LogSource,
}
```

This design is intentional: there are not enough dynamic cases to justify four separate computed hooks or four separate traits, and there is also no reason to force `&self` helpers that create avoidable clones.

The use of `meta = "computed"` is explicitly limited in this task. The allowed computed cases are:

- `PgInfoLogEvent::SqlTransition`
  The generated by-value arm or a small helper may compute:
  `severity`, `result`, `message`, and `source`
  Even though `message` and `source` will likely remain constant in practice, this is acceptable because the whole metadata block is computed together.

- `SubprocessLogEvent::Line`
  The generated by-value arm or a small helper may compute:
  `severity`, `result`, `message`, and `source`
  In practice `severity` depends on `stream`, `message` is the line text, `transport` depends on `stream`, while `result`, `producer`, and `parser` may remain constant.
  The line text must not be duplicated into structured fields such as `line` or `raw_line`.

- `PostgresLineLogEvent::Json`
  The generated by-value arm or a small helper may compute:
  `severity`, `result`, `message`, and `source`
  In practice `severity` and `message` come from the parsed line, `source` comes from the stored `PostgresLineSource`, and `result` will likely remain constant `ok`.

- `PostgresLineLogEvent::Plain`
  The generated by-value arm or a small helper may compute:
  `severity`, `result`, `message`, and `source`
  In practice `severity` and `message` come from the parsed line, `source` comes from the stored `PostgresLineSource`, and `result` will likely remain constant `ok`.

- `PostgresLineLogEvent::Unparsed`
  The generated by-value arm or a small helper may compute:
  `severity`, `result`, `message`, and `source`
  In practice `message` is the raw line text, `source` comes from the stored `PostgresLineSource`, while `severity` and `result` will likely remain constant.

No other event variant may use `meta = "computed"` unless this task is updated first. In particular:
- `RuntimeLogEvent::StartupEntered` must be fully static apart from normal field extraction.
- all `DcsLogEvent` variants must be fully static apart from normal field extraction.
- all `ProcessLogEvent` variants must be fully static apart from normal field extraction.
- `PostgresIngestLogEvent` variants must be fully static apart from normal field extraction.

**Required logger-owned global context:**

The logger-owned context must be:

```rust
#[derive(Clone, Debug, PartialEq, Eq)]
pub(crate) struct LogContext {
    pub(crate) hostname: String,
    pub(crate) cluster_name: String,
    pub(crate) scope: String,
    pub(crate) member_id: String,
}
```

This context is owned by logging and injected automatically by `LogSender` during record materialization. No application log event enum may contain these fields anymore.

This does not require changing the internal semantic shape of `LogEventDto`. It is acceptable and preferred for `LogEventDto` to keep internal fields such as `event_name`, `result`, and `source`. The dotted naming requirement applies to the final sink-facing serialized `LogRecord` schema, not to the internal DTO field names used inside logging.

**Required final record shape:**

The sink-facing record type must be flat:

```rust
#[derive(Clone, Debug, PartialEq, serde::Serialize)]
pub(crate) struct LogRecord {
    pub(crate) timestamp_ns: i64,
    #[serde(rename = "host.name")]
    pub(crate) hostname: String,
    #[serde(rename = "pgtm.cluster_name")]
    pub(crate) cluster_name: String,
    #[serde(rename = "pgtm.scope")]
    pub(crate) scope: String,
    #[serde(rename = "pgtm.member_id")]
    pub(crate) member_id: String,
    pub(crate) severity_text: LogSeverity,
    pub(crate) severity_number: u8,
    pub(crate) message: String,
    #[serde(rename = "event.name")]
    pub(crate) event_name: &'static str,
    #[serde(rename = "event.result")]
    pub(crate) event_result: LogEventResult,
    #[serde(rename = "source.producer")]
    pub(crate) producer: LogProducer,
    #[serde(rename = "source.transport")]
    pub(crate) transport: LogTransport,
    #[serde(rename = "source.parser")]
    pub(crate) parser: LogParser,
    #[serde(flatten)]
    pub(crate) attributes: std::collections::BTreeMap<String, serde_json::Value>,
}
```

This is a hard requirement. Do not emit nested `context`, nested `fields`, or nested `source` objects in the final JSONL record shape. The only tolerated nested flattening exception is the compile-time flattening of postgres payload keys into flat prefixed attributes.

This requirement exists specifically so the output stays easy to query in Grafana/Loki-style environments and stays conceptually closer to OTel attributes.

The final naming rule for sink-facing JSON is:
- the unprefixed top-level envelope fields are only:
  `timestamp_ns`, `severity_text`, `severity_number`, `message`
- logger/global metadata uses dotted names:
  `host.name`, `pgtm.cluster_name`, `pgtm.scope`, `pgtm.member_id`
- event metadata uses dotted names:
  `event.name`, `event.result`
- source metadata uses dotted names:
  `source.producer`, `source.transport`, `source.parser`
- domain/event-specific attributes emitted by the derive should prefer dotted prefixes when they represent namespaced concepts, for example:
  `job.kind`, `postgres.path`, `postgres.level_raw`, `dcs.mode.previous`, `dcs.mode.next`

The derive and field attributes must support this naming style directly. `#[log(key = "job.kind")]` is valid and preferred over bare generic keys like `job_kind` when the field is part of a stable namespaced schema.

`LogSender` must remain the only emission surface visible outside logging, and it must look like this:

```rust
#[derive(Clone)]
pub(crate) struct LogSender {
    // private fields only
}

impl LogSender {
    pub(crate) fn send<E>(&self, event: E) -> Result<(), LogSendError>
    where
        E: LoggableEvent,
    {
        // private implementation
    }
}

#[derive(Debug, thiserror::Error)]
pub(crate) enum LogSendError {
    #[error("log queue is closed")]
    QueueClosed,
}
```

The queue item type stays private to `src/logging`. It should be one private materialized shape derived from `LogEventDto` plus logger context and timestamp.

This task requires all application logging in the repo to go through this method. There must not be alternate logging paths left behind for “early startup” or “before the logger is really started”. If startup ordering prevents typed logging today, reorder startup so the logger boots earlier, and route those application logs through `LogSender` as well. The only exceptions are:
- typed bootstrap/config errors returned before logging is bootstrapped
- last-resort direct stderr diagnostics inside logging bootstrap itself if logging bootstrap fails before a usable `LogSender` exists

Outside those two exceptions, all application logging must use `LogSender::send(event)` and the new derive-based system. This is a cleanup task, not a partial adoption task.

**Exact required bootstrap error model:**

Bootstrap/configuration failures are not log events because logging is not usable until bootstrap succeeds. The current stringly bootstrap errors must be replaced with typed variants. The minimum required enum is:

```rust
#[derive(Debug, thiserror::Error)]
pub(crate) enum LogBootstrapError {
    #[error("file sink enabled but no file path was configured")]
    FileSinkPathMissing,
    #[error("file sink init failed for `{path}`: {cause}")]
    FileSinkInit { path: std::path::PathBuf, cause: String },
}
```

If more typed bootstrap variants are needed during implementation, add them in this same spirit. Do not regress back to `Misconfigured(String)` or `SinkInit(String)`. Do not invent bootstrap log events such as `LogBootstrapPathNotSetError`; that is the wrong lifecycle layer.

`meta = "computed"` is the only dynamic metadata marker in the proc-macro contract. It means the macro-generated impl handles that variant with a by-value computed metadata path instead of fixed static metadata literals.

That is the only allowed reason to keep a small handwritten helper on an event enum. The normal case must be fully declarative on attributes.

**Exact semantic rules for the exhaustive event set:**
- All app-domain events (`RuntimeLogEvent`, `PgInfoLogEvent`, `DcsLogEvent`, `ProcessLogEvent`, `PostgresIngestLogEvent`) use `producer = App`, `transport = Internal`, `parser = App`.
- `SubprocessLogEvent::Line` uses `producer = PgTool`, `transport = ChildStdout | ChildStderr`, `parser = Raw` based on `CapturedStream`.
- `SubprocessLogEvent::Line` uses the subprocess line text as the top-level `message` and must not duplicate that text into a structured attribute.
- `PostgresLineLogEvent::Json` uses `parser = PostgresJson`.
- `PostgresLineLogEvent::Plain` uses `parser = PostgresPlain`.
- `PostgresLineLogEvent::Unparsed` uses `parser = Raw`.
- For all failure detail fields, the field name is `cause`, never `error`.
- `scope`, `member_id`, `cluster_name`, and `hostname` never appear in any event enum payload. They are logger context only.
- `job_id` and `binary` are removed from logging entirely.
- `bytes_len` is removed from logging entirely.
- `message` remains the top-level human-readable summary line in `LogEventDto` / `LogRecord`.
- `event_name` is the stable machine-readable event identifier.
- `event_domain` is removed entirely because event names are already namespaced.
- The final serialized `LogRecord` must expose `event.name`, `event.result`, `source.producer`, `source.transport`, `source.parser`, `host.name`, `pgtm.cluster_name`, `pgtm.scope`, and `pgtm.member_id` as dotted flat keys.
